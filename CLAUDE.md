## Project overview

HRChatpot is a Django-based HR chatbot. It has a single Django app, `chatpot`. Employees ask HR-policy questions and get answers via retrieval-augmented generation (RAG): relevant chunks are retrieved from embedded HR policy PDFs and an answer is generated by Together AI's LLM API. `INTERVIEW_PREP.md` at the repo root is a self-authored deep-dive on this project (request-flow walkthrough, architecture diagram, design trade-off Q&A) — worth reading for more detail than this file covers, though it still describes the original Mistral-based LLM config.

## Environment

The committed `hrchatpotenv/` folder (Python 3.12.7) *is* the project's virtual environment — there is no separate named conda env for this project. Its `pyvenv.cfg` shows it was created by running conda's **base** Python (`anaconda3\python.exe`) through the standard `venv` module (`python -m venv hrchatpotenv`), not `conda create -n <name>`. All named conda envs on this machine were checked directly and none has this project's full dependency combo (Django 5.2 + langchain + faiss + mysqlclient together).

No `requirements.txt`/`Pipfile`/`pyproject.toml` exists — dependencies only exist as the packages already installed in `hrchatpotenv/`. ## Commands

Repo layout gotcha: `manage.py` lives at `hrchatpot/manage.py` (one level under repo root), and the Django project config package is *also* named `hrchatpot`, at `hrchatpot/hrchatpot/`. All `manage.py` commands must be run from `hrchatpot/` (the dir containing `manage.py`), not repo root.

**Run the app** (Windows, from repo root):
```powershell
hrchatpotenv\Scripts\activate
cd hrchatpot
# put your real key in hrchatpot\.env (TOGETHER_API_KEY=...) — see Required env vars below
python manage.py migrate
python manage.py runserver
```
Then visit `http://127.0.0.1:8000/login/` (or `/admin/`). Prerequisite: a MySQL server must already be running and reachable at the hardcoded settings (host `localhost`, port `3306`, db `hrchatbot`, user `root`, password `SamShalomJoshua` — see Known issues below). `migrate` creates tables inside that database but not the database itself, so `hrchatbot` must already exist.

**Recover/create app login credentials** (from `hrchatpot/`, venv active):
- No usable username at all: `python manage.py createsuperuser` — the custom `User` model defaults `role` to `EMPLOYEE`, so for HR access (needed for `/upload/`) set `role='HR'` afterward via `/admin/` or the shell (see below).
- Know the username but not the password: `python manage.py changepassword <username>`.
- Don't know what usernames exist: `python manage.py shell` then `from chatpot.models import User; list(User.objects.values_list("username", "role"))`.

**Tests**: `python manage.py test` (from `hrchatpot/`) — `chatpot/tests.py` is currently empty/boilerplate, so this runs nothing meaningful yet.

**Required env vars**: `TOGETHER_API_KEY` — set it in `hrchatpot/.env` (same dir as `manage.py`; gitignored). `settings.py` calls `load_dotenv(BASE_DIR / ".env")` right after `BASE_DIR` is defined, so the key is loaded into the process env at Django startup and read via `os.getenv` in `chatpot/utils/query_engine.py` at call time.

## Architecture

- **Nesting**: repo root → `hrchatpot/` (contains `manage.py`) → `hrchatpot/` (Django project config: `settings.py`, `urls.py`, `wsgi.py`, `asgi.py`) and `chatpot/` (the one Django app). All URL routing lives in the *project-level* `hrchatpot/hrchatpot/urls.py` — `chatpot` has no `urls.py` of its own.
- **Auth/users**: custom user model `chatpot.User` (extends `AbstractUser`, adds a `role` choice field: `HR`/`IT`/`EMPLOYEE`), set as `AUTH_USER_MODEL`. `is_hr(user)` in `chatpot/views.py` gates the `/upload/` route via `user_passes_test`.
- **Routes** (`hrchatpot/hrchatpot/urls.py`): `index` (chat page, resets session chat history), `ask/` (POST, chatbot answer endpoint — returns an HTML fragment consumed by client-side `fetch` JS, not a full page), `admin/`, `login/`/`logout/` (Django built-in auth views), `''` root → `dashboard` (post-login landing page), `upload/` (HR-only ZIP upload of policy docs), `test/` (undecorated leftover route, not part of the real feature set).
- **RAG chatbot pipeline** (the core of the app):
  - `chatpot/utils/embedding_loader.py` extracts text from policy PDFs via PyMuPDF (`fitz`), chunks with `RecursiveCharacterTextSplitter` (chunk_size=500, overlap=100), embeds with `HuggingFaceEmbeddings` (`sentence-transformers/all-MiniLM-L6-v2`), and builds/saves a local FAISS index to `chatpot/vectorstore/`. `load_and_save_embeddings()` in this file is dead/broken code (unused `OpenAIEmbeddings` path, references an unimported `PyPDFLoader`) — it is not the real embedding path.
  - `chatpot/utils/query_engine.py`'s `answer_query(query)` loads the same HF embeddings, loads the FAISS index (`allow_dangerous_deserialization=True`), retrieves the top-3 chunks, and answers via LangChain `RetrievalQA` using `ChatOpenAI` pointed at **Together AI's** OpenAI-compatible endpoint (`https://api.together.ai/v1`, model `openai/gpt-oss-20b`, key from `TOGETHER_API_KEY`). Despite the `openai` package/class names, inference goes through Together AI, not OpenAI directly. (Originally used Mistral's API — switched after Mistral moved to a paid billing tier.) `gpt-oss-20b` is a reasoning model, so the call passes `model_kwargs={"reasoning_effort": "low"}` and an explicit `max_tokens=512` — without those, an earlier reasoning model (`Qwen/Qwen3.5-9B`) consumed its whole token budget on internal chain-of-thought and returned an empty final answer.
  - Source docs: seed set in `chatpot/policies/*.pdf` (9 HR policy PDFs). HR users can replace these via `/upload/` (uploads a ZIP → extracted to `chatpot/uploaded_docs/` → `process_policy_documents()` rebuilds the FAISS vectorstore).
  - Chat history is kept in the Django session (`session['chat_history']`), not persisted to any model/DB. Session history stores the LLM's raw markdown answer (unformatted) — it isn't currently rendered anywhere, so this doesn't need to match what's shown in the chat window.
  - The LLM answers in markdown (bold, tables, etc.). `chatpot/views.py`'s `format_answer()` converts it to HTML via `markdown.markdown(answer, extensions=["tables"])` and sanitizes it with `bleach.clean()` (allowlisted tags only — the LLM's output is not fully trusted input, so raw HTML is not passed through) before `ask_question` wraps it in the response div. `chatpot/templates/chatpot/index.html`'s JS sets `innerHTML` (not `textContent`) on bot messages to actually render that HTML — this depends on the server already having sanitized it.
- **Templates** (`chatpot/templates/chatpot/`): `base.html` is the real shared layout (inline `<style>`, sidebar nav, `{% block content %}`) — `index.html`, `dashboard.html`, `upload.html` extend it; `login.html` stands alone (used by Django's built-in `LoginView`). `header.html` and `footer.html` are unused leftover starter-template boilerplate (blog-themed, not `{% include %}`'d anywhere) — don't treat them as part of the real layout.
- **Database**: `settings.py` is configured for MySQL (`hrchatbot` DB) — the `db.sqlite3` file present in `hrchatpot/` is a vestigial/unused artifact. Only one real migration exists (`chatpot/migrations/0001_initial.py`); stale compiled `.pyc` files for migrations 0002/0003 exist in `__pycache__` with no corresponding source — migration history was squashed/rewritten at some point, so don't expect 0002/0003 to exist.
